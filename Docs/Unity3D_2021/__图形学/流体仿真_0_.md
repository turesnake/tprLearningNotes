2d fire 示范程序用的是 cpu 版最简单的程序:
遍历 grid 中每个 cell, 根据其四周4个 u/v 值计算这个 cell 的 散度, 然后把这个散度反设置回去;

这是 Gauss–Seidel 法, 在 cpu 端这是 ok 的;
想要变成 gpu 版, 需要动动脑子

你使用的：
    Gauss–Seidel Pressure Projection
    Red–Black (棋盘格 / Graph Coloring) 迭代
    在网格上操作 U,V 分量
    这属于 Stable Fluids 的压力投影阶段（即解 Poisson 方程部分）的简化版：

问题在于：
    同步读写 (write conflict) —— GPU 中并行线程更新邻居格点时会导致竞态；
    棋盘格 artifact —— 由于更新模式周期性不均，引入伪压缩模式；
    Gauss–Seidel 不可很好并行化 —— GPU 更适合 Jacobi 或 Multigrid 等结构化算法；
    边界处理不完全正确时，压力流失或漂移。



# !!!! 不能在 gpu 版中用 棋盘格双色法 !!!!!
    会出现 梳子状的条纹;
    每个格子间隔出现, 假设 pass1 中计算出了正值, 则会一起挤压 pass2 的那些格子
    这么迭代几次后, 就会出现震荡



# 主流可替代的 GPU 稳定算法
# Jacobi Pressure Solver（最常用 GPU 投影法）
最经典、最广泛使用的 GPU 压力投影实现（Unity URP / Unreal / Frostbite 都有变种）。

每一帧：
    for i in iterations:
        p[w,h] = ( (p[w-1,h] + p[w+1,h] + p[w,h-1] + p[w,h+1]) - div[w,h] ) / 4
    ---
    感觉是要计算出每个格子的压强 p, 然后统一匀一下

特点：
    完全可并行（每像素单独算，不依赖邻居更新）；
    没有写竞争；
    缺点是收敛较慢，但 20~40 次就够游戏使用； ????/
    支持多 pass “ping-pong” buffer；
    可结合 shared memory（local cache）提高效率。


# Multigrid Pressure Solver（多重网格法）
    工业级算法，如 Houdini、NVIDIA Flow 使用。

    原理：先在低分辨率网格上求解大尺度压力，再递归细化到高分辨率。
    优点是收敛极快 (O(N))，但 GPU 实现复杂，需要层级 buffer。

    ✅ 更适合高端真实流体项目或大规模格点 (>512²)。



# Lattice Boltzmann Method (LBM)
    基于流体分布函数的统计法：

    本质是局部更新、无全局依赖；
    理论上天然并行；
    对于 2D/3D GPU 仿真（如烟雾/云流）非常高效；
    可用 D2Q9 模型 (9 velocity vectors per cell)。
    典型参考：
    Kara et al. - "Real-Time Lattice-Boltzmann Fluid Simulation on GPUs" (2010)

    ✅ 优点：稳定、无需压力投影；
    ❌ 缺点：改写复杂度较高，物理调参较难。



# Position-Based Fluids (PBF)
    如果你的项目更像粒子/游戏性 (而非 Navier-Stokes 物理解算)，PBF 是主流：

    基于对密度约束的迭代，实现近似不可压缩；
    从 SPH 演进而来；
    被 Unity VFX Graph、NVIDIA Flex、UE Water System 广泛采用；
    完全 GPU friendly；
    对稳定性非常耐打。
    ✅ 优点：快速、稳定。
    ❌ 缺点：不是严格流体动力学（近似行为式）。

# Red-Black Gauss-Seidel on GPU（使用两次 kernel 的 Jacobi-like）
    概念：用棋盘（红黑）分裂，红点和黑点交替更新。你当前用的两-pass Gauss-Seidel 本质如此，但在 GPU 上会出现写冲突/同步问题。
    优点：收敛快于纯 Jacobi（通常 2x）；实现比多重网格简单。
    缺点：在 GPU 需要严格两次 kernel（红->黑），但若每个 kernel 内仍更新邻居会发生并行写竞争；
        安全实现要求每个 pass 只写自己的格点（pressure grid 的红/黑），不去直接写 U/V（velocity 的写操作必须在 projection 完成后集中做）。
    实现建议：
        仅对 pressure 网格做 Red/Black 更新（每个 kernel 写入 p 的自己的色点）；这样不会发生对 U/V 的并发写冲突。
        
    最后再用统一 kernel 根据最终 p 修正 U/V（避免在内部同时更新 U 的场景，正是你代码中导致 artifact 的写冲突）。
    对 artifact 的作用：如果你把 U/V 更新延后到 projection 结束，能减少或消除 checkerboard，但仍比 Jacobi 复杂并且容易错误。

# == 新 不可压约束:
	Compute Divergence（散度）
	    用更新后的 U/V 求出当前散度场。
	    这是不可压约束求解器的输入。

	Pressure Solve (投影步骤) -- [迭代多次]
	    Red‑Black Gauss‑Seidel 或 Jacobi 求解压力 p。

	Subtract Gradient (投影)
	    按 ∇p 修正 U/V，使新的速度场 “无散度” (div ≈ 0)。
